## 1. Non-negotiable principles

1. **Modular Monolith** in one monorepo. Forbidden: microservices, Kubernetes, Redis, MediatR, Generic Repository.
2. **Strict multi-tenancy:** every tenant-scoped entity carries `TenantId (Guid)`; a global EF Core query filter plus a `SaveChanges` interceptor that rejects any write without a resolvable `TenantId`.
3. **Tenant resolution (v1.2):** a **single platform bot** validates `Telegram.WebApp.initData` (HMAC-SHA256 against the one platform `TELEGRAM_BOT_TOKEN`). The validated `telegram_user_id` is then mapped to a tenant by:
   - **Storefront:** the `{shopSlug}` route segment → `Tenant.Slug`.
   - **Merchant:** the caller's `TenantMember` rows; if exactly one, it is selected automatically; if several, the client must call `/auth/switch-tenant`.
   The resolved tenant is carried in the JWT as `tenant_id`, alongside `role`.
4. **Roles:** `PlatformAdmin` (future, no refactor), `MerchantOwner`, `MerchantStaff`, `Customer`. `PlatformAdmin` is served from `/api/v1/platform/**` under a separate policy — **not** via `TenantId`.
5. **Contract-first API:** OpenAPI is generated by the backend; the frontend consumes only generated types (`openapi-typescript` + `openapi-fetch`). Hand-written DTOs are forbidden.
6. **Bilingual + RTL:** i18next with `fa`/`en`, Radix `DirectionProvider`, all layouts use logical properties (`ms-*`, `me-*`).
7. **Reliability:** transactional Outbox in PostgreSQL + `BackgroundService`; `IFileStorageService` with a local-volume implementation in MVP; atomic stock decrement guarded by a concurrency token.

## 2. Data model (MVP — PostgreSQL)

All tables: `Id (Guid, PK)`, `CreatedAt (timestamptz)`, `UpdatedAt (timestamptz)`. Entities marked `*` are tenant-scoped and carry `TenantId (Guid, NOT NULL, FK → Tenant.Id, ON DELETE RESTRICT)`.

| Entity | Key fields | Constraints / notes |
|---|---|---|
| `Tenant` (Shop) | `Slug`, `Name`, `DefaultLanguage`, `Currency`, `IsActive` | Root of tenancy. `Slug` UNIQUE globally, `^[a-z0-9-]{3,40}$`. **No `BotToken` column in MVP** (v1.2) — the platform bot is global config. |
| `User` | `TelegramUserId (bigint)`, `FirstName`, `LastName`, `LanguageCode` | Platform-level identity. `TelegramUserId` UNIQUE globally. Not tenant-scoped. |
| `TenantMember`* | `TenantId`, `UserId`, `Role` | UNIQUE `(TenantId, UserId)`. `Role ∈ {MerchantOwner, MerchantStaff}`. A user may belong to several shops (hence `/auth/switch-tenant`). |
| `Category`* | `Name`, `NameEn`, `Slug`, `SortOrder`, `IsActive` | UNIQUE `(TenantId, Slug)`. `SortOrder` int, default 0. |
| `Product`* | `CategoryId`, `Name`, `NameEn`, `Description`, `Price`, `Stock`, `IsActive`, `RowVersion` | `Price numeric(18,2) ≥ 0`; `Stock int ≥ 0`; `RowVersion` = concurrency token. FK `CategoryId` → `Category.Id` ON DELETE RESTRICT. **`ImageUrl` removed in v1.2** — images live in `ProductImage`. |
| `ProductImage`* | `ProductId`, `StoragePath`, `AltText`, `SortOrder`, `IsPrimary` | FK `ProductId` → `Product.Id` ON DELETE CASCADE. `SortOrder` int default 0. **Partial UNIQUE `(ProductId) WHERE IsPrimary`** — at most one primary image per product. `StoragePath` is a tenant-namespaced key from `IFileStorageService`. |
| `Customer`* | `TelegramUserId`, `DisplayName`, `Phone`, `Notes` | UNIQUE `(TenantId, TelegramUserId)`. `Phone` nullable, E.164 when present. |
| `Tag`* | `Name` | UNIQUE `(TenantId, Name)`. |
| `CustomerTag`* | `CustomerId`, `TagId` | Composite PK `(CustomerId, TagId)`; both FKs ON DELETE CASCADE. |
| `Order`* | `CustomerId`, `Status`, `TotalAmount`, `Note`, `PlacedAt`, `RowVersion` | `Status` enum stored as `text` with a CHECK constraint (§3). `TotalAmount numeric(18,2) ≥ 0`, computed server-side from items — never trusted from the client. |
| `OrderItem`* | `OrderId`, `ProductId`, `ProductNameSnapshot`, `UnitPrice`, `Quantity` | `Quantity int > 0`; `UnitPrice numeric(18,2) ≥ 0`. Price and name are **snapshotted** at order time. FK `OrderId` ON DELETE CASCADE; `ProductId` ON DELETE RESTRICT. |
| `OrderStatusHistory`* | `OrderId`, `FromStatus`, `ToStatus`, `ActorUserId`, `ActorRole`, `Reason`, `OccurredAt` | **New in v1.2.** Append-only audit of every transition. FK `OrderId` → `Order.Id` ON DELETE CASCADE. `FromStatus` nullable (the creation row: `null → Pending`). Index `(OrderId, OccurredAt)`. No UPDATE/DELETE path in the application. |
| `OutboxMessage` | `Type`, `Payload (jsonb)`, `OccurredAt`, `ProcessedAt`, `Attempts`, `LastError`, `TenantId (nullable)` | Index on `ProcessedAt IS NULL`. `Attempts int` default 0. `TenantId` nullable column for filtering; also embedded in `Payload`. |
| `ShopSetting`* | `TenantId`, `Key`, `Value` | Composite UNIQUE `(TenantId, Key)`. `Value` jsonb. |

**Mandatory indexes:** UNIQUE `(TenantId, Slug)` on `Category`; UNIQUE `(TenantId, TelegramUserId)` on `Customer`; `(ProcessedAt)` on `OutboxMessage`; `(TenantId, Status, PlacedAt DESC)` on `Order`; `(TenantId, IsActive)` on `Product`; `(ProductId, SortOrder)` on `ProductImage`; `(OrderId, OccurredAt)` on `OrderStatusHistory`.

**Money & time:** all money `numeric(18,2)`; all timestamps `timestamptz` in UTC, rendered in the shop timezone on the client.

## 3. Order Status State Machine

States: `Pending`, `Confirmed`, `Preparing`, `Shipped`, `Delivered`, `Cancelled`.

```
                 ┌──────────────► Cancelled ◄──────────────┐
                 │                    ▲                    │
  Pending ──► Confirmed ──► Preparing ──► Shipped ──► Delivered
     │             │             │            │
     └─────────────┴─────────────┴────────────┘
        (cancel allowed up to and including Shipped)
```

**Allowed transitions (the only legal edges):**

| From | To | Actor | Guard |
|---|---|---|---|
| `Pending` | `Confirmed` | MerchantOwner / Staff | — |
| `Pending` | `Cancelled` | Customer (own order) / Merchant | **stock restored (idempotent)** |
| `Confirmed` | `Preparing` | Merchant | — |
| `Confirmed` | `Cancelled` | Merchant | stock restored (idempotent) |
| `Preparing` | `Shipped` | Merchant | — |
| `Preparing` | `Cancelled` | Merchant | stock restored (idempotent) |
| `Shipped` | `Delivered` | Merchant | — |
| `Shipped` | `Cancelled` | Merchant | stock restored (idempotent, manual reconciliation) |
| `Delivered` | — | — | **terminal** |
| `Cancelled` | — | — | **terminal** |

**Rules:**

1. Any transition not in the table above returns `409 Conflict` with `code: "invalid_status_transition"` and the current status in `extensions.currentStatus`.
2. `Delivered` and `Cancelled` are terminal — no further transition, ever.
3. **Stock decrement:** atomic at order creation — `UPDATE "Products" SET "Stock" = "Stock" - @q WHERE "Id" = @id AND "Stock" >= @q`; 0 rows affected → `409 insufficient_stock`, whole transaction rolled back.
4. **Stock restore (v1.2 — corrected):** **every** transition into `Cancelled` restores stock, including `Pending → Cancelled`. The restore is **idempotent** and safe under retry/concurrency:
   - The restore runs **inside the same transaction** as the status change, and only after a conditional update `UPDATE "Orders" SET "Status" = 'Cancelled' WHERE "Id" = @id AND "Status" = @fromStatus` reports exactly 1 row. If 0 rows, the transition is rejected (`409 concurrency_conflict`) and **no** stock is touched.
   - Because `Cancelled` is terminal and the conditional update can only succeed once, the restore can never run twice for the same order.
   - A `Pending` order has already decremented stock at creation, so restoring on `Pending → Cancelled` is required — this was the v1.1 defect.
   - Restore is a single set-based statement per order item: `UPDATE "Products" SET "Stock" = "Stock" + @q WHERE "Id" = @id` (no `Stock >=` guard — restoring must never fail).
5. **Side effects** are never executed inline. Each transition writes an `OutboxMessage` (`order.status_changed`) in the same transaction; the `BackgroundService` delivers the Telegram notification. A failed Telegram call never rolls back the status change.
6. **Audit (v1.2):** every transition — including order creation — appends one `OrderStatusHistory` row `(OrderId, FromStatus, ToStatus, ActorUserId, ActorRole, Reason, OccurredAt)` in the same transaction. The table is append-only; there is no update or delete path.
7. **Concurrency:** `Order` carries a `RowVersion`; a stale update returns `409 concurrency_conflict`.

## 4. REST API contract (summary — full detail in `contracts/openapi.json`)

Prefix `/api/v1`. Errors are RFC 7807 `ProblemDetails` with a machine-readable `code`. Paging is `?page=&pageSize=` returning `{ items, total, page, pageSize }`.

### 4.1 Auth — `/api/v1/auth`

| Method | Route | Auth | Purpose |
|---|---|---|---|
| `POST` | `/api/v1/auth/telegram` | none (initData in body) | Validate `initData` → `{ accessToken, expiresAt, user, tenants[], activeTenant? }` |
| `POST` | `/api/v1/auth/switch-tenant` | Bearer | Body `{ tenantId }` → new token scoped to that tenant. `403` if the caller is not a `TenantMember` of it. |

### 4.2 Merchant onboarding — `/api/v1/merchants`

| Method | Route | Auth | Purpose |
|---|---|---|---|
| `POST` | `/api/v1/merchants` | Bearer (any authenticated user) | Create a shop; caller becomes `MerchantOwner`. Body `{ name, slug, defaultLanguage, currency }`. `409 slug_taken` on collision. |
| `GET` | `/api/v1/merchants/mine` | Bearer | Shops the caller belongs to (drives the tenant switcher). |

### 4.3 Merchant back-office — `/api/v1/merchant/**` (policy `Merchant`, requires `tenant_id`)

| Area | Routes |
|---|---|
| Categories | `GET/POST /merchant/categories` · `GET/PATCH/DELETE /merchant/categories/{id}` |
| Products | `GET/POST /merchant/products` · `GET/PATCH/DELETE /merchant/products/{id}` |
| Stock | `POST /merchant/products/{id}/stock-adjust` — body `{ delta, reason }`; `409 insufficient_stock` if it would go negative |
| Product images | `GET/POST /merchant/products/{id}/images` · `PATCH/DELETE /merchant/products/{id}/images/{imageId}` · `POST /merchant/products/{id}/images/{imageId}/primary` |
| Customers | `GET/POST /merchant/customers` · `GET/PATCH /merchant/customers/{id}` |
| Customer orders | `GET /merchant/customers/{id}/orders` |
| Tags | `GET/POST /merchant/tags` · `DELETE /merchant/tags/{id}` · `POST /merchant/customers/{id}/tags` · `DELETE /merchant/customers/{id}/tags/{tagId}` |
| Orders | `GET /merchant/orders` · `GET /merchant/orders/{id}` · `PATCH /merchant/orders/{id}/status` · `GET /merchant/orders/{id}/history` |
| Settings | `GET/PUT /merchant/settings` |

### 4.4 Storefront — `/api/v1/storefront/{shopSlug}/**` (public read, customer auth for cart/orders)

| Method | Route | Auth | Purpose |
|---|---|---|---|
| `GET` | `/storefront/{shopSlug}` | none | Public shop info (name, currency, language) |
| `GET` | `/storefront/{shopSlug}/categories` | none | Active categories |
| `GET` | `/storefront/{shopSlug}/products` | none | Active products; `?categoryId=&q=&page=&pageSize=` |
| `GET` | `/storefront/{shopSlug}/products/{id}` | none | Product detail incl. images |
| `POST` | `/storefront/{shopSlug}/cart/validate` | Bearer (Customer) | Validate cart lines + stock → priced summary |
| `POST` | `/storefront/{shopSlug}/orders` | Bearer (Customer) | Place order — **`Idempotency-Key` header mandatory** |
| `GET` | `/storefront/{shopSlug}/orders` | Bearer (Customer) | Own orders list |
| `GET` | `/storefront/{shopSlug}/orders/{id}` | Bearer (Customer) | Own order detail + status history |
| `POST` | `/storefront/{shopSlug}/orders/{id}/cancel` | Bearer (Customer) | Cancel own order — allowed only from `Pending`; restores stock |

`{shopSlug}` is resolved to a `Tenant` before any query; an unknown or inactive slug returns `404 shop_not_found`. A customer token is always scoped to the tenant of the slug it was issued for — a token for shop A used on shop B's slug returns `404`.

### 4.5 Telegram webhook — `/api/v1/telegram/webhook`

| Method | Route | Auth | Purpose |
|---|---|---|---|
| `POST` | `/api/v1/telegram/webhook` | `X-Telegram-Bot-Api-Secret-Token` header (constant-time compare) | Single platform bot update receiver. Handles `/start` deep links (`/start shop_{slug}`) and routes the user into the Mini App. Always returns `200` fast; real work is queued to the outbox. |

### 4.6 Platform (future — policy skeleton only)

- `/api/v1/platform/**` — policy `PlatformAdmin`, no `TenantId`.

**Status codes:** `200/201/204` success · `400` validation (`validation_failed` + field map) · `401` missing/invalid token · `403` role mismatch or not a member of the requested tenant · `404` not found **or cross-tenant access** (never `403` for cross-tenant — see §6) · `409` state/concurrency/stock/slug · `422` business rule · `429` rate limited.

## 5. Auth & Session strategy for the Telegram WebView

**5.1 Identity bootstrap.** The Mini App calls `Telegram.WebApp.initData` (raw query string). The client POSTs it to `/api/v1/auth/telegram`. The server:

1. Parses the query string, extracts `hash`, removes it, sorts remaining key=value pairs lexicographically, joins with `\n`.
2. Computes `secret_key = HMAC_SHA256(key="WebAppData", msg=TELEGRAM_BOT_TOKEN)` — the **single platform bot token** from configuration (v1.2).
3. Computes `HMAC_SHA256(key=secret_key, msg=data_check_string)` and compares to `hash` in **constant time**.
4. **Replay window (v1.2 — configurable):** rejects if `now - auth_date > Auth:InitDataMaxAgeSeconds` → `401 init_data_expired`. **Default `86400` (24 h)**; the value is read from configuration and may be lowered per environment (e.g. `300` in production if the client always re-bootstraps). It is never hard-coded.
5. Upserts `User` by `TelegramUserId`, loads the caller's `TenantMember` rows, and issues a token. If the user has exactly one membership it becomes `activeTenant`; if several, `activeTenant` is `null` and the client must call `/auth/switch-tenant`; if none, the token is issued with no `tenant_id` (enough to call `POST /merchants`).

**5.2 Token model.** A single **access JWT**, HS256, `exp` = **60 minutes**, claims: `sub` (UserId), `telegram_user_id`, `tenant_id` (absent when no active tenant / PlatformAdmin), `role`, `jti`. No refresh token in MVP — the Mini App re-runs `initData` bootstrap silently on `401` (initData is always available inside Telegram, so re-auth is free). A refresh-token flow is deferred to P5 and would require an ADR.

**5.3 Client storage inside the WebView.** The token lives **in memory** (React context / TanStack Query cache) and is mirrored to `sessionStorage` only, so a WebView reload does not force a re-bootstrap. **`localStorage` is forbidden** for the token. On `401`, the client clears the token, re-runs bootstrap once, and retries the original request once; a second `401` surfaces a re-open-the-app state.

**5.4 Transport & headers.** HTTPS only. `Authorization: Bearer <jwt>`. The API never accepts `initData` on any route other than `/auth/telegram`. CORS is not needed (same-origin through the proxy) and must not be opened with `*`.

**5.5 Development bypass.** A `DevAuth` handler is enabled **only** when `ASPNETCORE_ENVIRONMENT=Development` **and** `Auth:AllowDevBypass=true`; it is hard-disabled in `Production` by a startup guard that throws if the flag is set. It must never be reachable in a deployed environment.

**5.6 PlatformAdmin.** Separate policy, separate claim set, no `tenant_id`. Routes under `/platform/**` are excluded from the tenant filter by an explicit `IgnoreQueryFilters` scope reachable only from that policy — never from a merchant or customer route.

**5.7 WebView constraints.** The Mini App must work with `X-Frame-Options` replaced by `Content-Security-Policy: frame-ancestors 'self' https://web.telegram.org https://*.telegram.org` (see P0 finding F-03). Session cookies are not used, so third-party-cookie blocking inside the WebView is irrelevant.

**5.8 Configuration keys (v1.2).**

| Key | Default | Notes |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | — (required) | Single platform bot. Fail-fast at startup if missing. |
| `TELEGRAM_WEBHOOK_SECRET` | — (required) | Compared against `X-Telegram-Bot-Api-Secret-Token`. |
| `Auth:InitDataMaxAgeSeconds` | `86400` | Replay window for `auth_date`. |
| `Auth:JwtLifetimeMinutes` | `60` | Access token lifetime. |
| `Auth:AllowDevBypass` | `false` | Only honoured in `Development`. |

## 6. Multi-tenancy isolation rules

1. **Every** tenant-scoped entity has `TenantId Guid NOT NULL` and a global query filter `e => e.TenantId == _tenantContext.TenantId`.
2. `ITenantContext` is resolved per-request from the `tenant_id` claim. If a tenant-scoped route is hit without a resolvable tenant, the request fails `401` **before** any query runs.
3. A `SaveChanges` interceptor stamps `TenantId` on inserts and **throws** if an insert has no tenant or an update attempts to change `TenantId`. There is no code path that writes a tenant-scoped row without a tenant.
4. **Cross-tenant access returns `404`, never `403`** — a `403` would confirm the existence of another tenant's resource. Enforced by the query filter, not by post-fetch checks.
5. All uniqueness constraints are **tenant-scoped** (`(TenantId, Slug)`, `(TenantId, TelegramUserId)`, `(TenantId, Name)`), so two shops may legitimately use the same slug/name. `Tenant.Slug` itself is globally unique because it is the storefront URL key.
6. **Single platform bot (v1.2):** there is no per-tenant bot token. The outbox worker sends every notification through the one platform bot; the recipient is the customer's `TelegramUserId` resolved **within the message's `TenantId`**. Tenant isolation therefore lives entirely in the data layer, not in bot credentials — which removes the per-tenant secret-storage surface.
7. File storage paths are namespaced `/{tenantId}/{entity}/{id}`; `IFileStorageService` takes the tenant id as a required argument. `ProductImage.StoragePath` is always produced by that service.
8. `PlatformAdmin` is the **only** principal allowed to cross tenants, and only through `/platform/**` with an explicit, audited `IgnoreQueryFilters` scope.
9. **Tests are mandatory:** every repository/service test suite must include a "tenant A cannot read/write tenant B" case. A phase is not accepted without it.

## 8. File-text handoff protocol

1. The owning agent builds files in its own workspace.
2. Publishes with `upload_file` → durable `/sites/...` URL.
3. In the handoff message to Agent 5: **exact repo path + file URL + one-line description** per file.
4. Agent 5 commits via the GitHub API on the phase branch (`feat/p{N}-{scope}`) and opens a PR.
5. Agent 4 reviews; merge only with green CI (squash).

**Branch naming:** `feat/p{N}-{scope}` — e.g. `feat/p1-backend-core`, `feat/p3-frontend-shell`.
