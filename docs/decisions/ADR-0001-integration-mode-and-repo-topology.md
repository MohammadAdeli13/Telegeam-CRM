# ADR-0001 — Integration Mode, Repository Topology & File Ownership

- **Status:** Accepted
- **Date:** 2026-11-25 (revised 2026-11-26 for contract v1.2)
- **Deciders:** Agent 1 (Team Lead & Software Architect), Agent 5 (DevOps & GitHub Repository Engineer)
- **Supersedes:** none
- **Related:** Phase 0 Contract v1.2 (`docs/architecture/phase-0-contract.md`)

---

## 1. Context

The project is a multi-tenant Telegram CRM & Mini App Storefront delivered by five agents working in **isolated sandboxes**. Verified environment constraints:

| Constraint | Consequence |
|---|---|
| Each agent run has its own isolated `/workspace`; no shared filesystem | Agents cannot read each other's files directly |
| `git push` from the sandbox fails (no credentials) | Commits must go through the GitHub API |
| Docker is not installed in the sandbox | `docker build` / `compose up` cannot be verified locally; CI does it |
| GitHub access is via Composio MCP (identity `MohammadAdeli13`, admin on `MohammadAdeli13/Telegeam-CRM`) | Repo writes are API calls, subject to MCP availability |
| MCP writes can return `403` | A write path must have a documented fallback |

Two integration modes were considered.

## 2. Decision

### 2.1 Integration mode — **Mode B: Sequential / Single-Integrator**

Agents do **not** commit concurrently. Each phase is produced by its owning agent, published as files, and committed by **one** integrator (Agent 5). Phases run in the fixed order P0 → P6.

**Rejected — Mode A (parallel multi-writer):** requires a shared filesystem and working `git push`, neither of which exists. Parallel writers on isolated sandboxes would produce conflicting trees with no way to reconcile them.

### 2.2 Handoff pattern — **File-Text Handoff**

1. The owning agent writes files in its own workspace.
2. Publishes each file with `upload_file` → a durable `/sites/...` URL.
3. Sends Agent 5 a handoff listing **exact repo path + file URL + one-line description** per file.
4. Agent 5 commits via the GitHub API on the phase branch and opens a PR.
5. Agent 4 reviews; merge only with green CI (squash).

### 2.3 Repository topology — **single monorepo**

```
telegram-crm/
├─ .github/workflows/          # CI (Agent 5)
├─ backend/
│  ├─ src/
│  │  ├─ Api/                  # ASP.NET Core 10 host, endpoints, auth, OpenAPI
│  │  ├─ Domain/               # entities, enums, state machine, domain rules
│  │  ├─ Application/          # use cases, validators, DTOs, interfaces
│  │  └─ Infrastructure/       # EF Core, migrations, outbox, file storage, Telegram
│  └─ tests/                   # xUnit + WebApplicationFactory
├─ frontend/
│  ├─ src/
│  │  ├─ app/                  # bootstrap, router, providers, i18n
│  │  ├─ features/             # storefront, cart, checkout, merchant dashboard
│  │  ├─ shared/               # ui, api client (generated), hooks, utils
│  │  └─ locales/              # fa.json, en.json
│  └─ e2e/                     # Playwright
├─ contracts/                  # openapi.json (generated by backend)
├─ docs/
│  ├─ architecture/            # phase-0-contract.md, overview
│  ├─ decisions/               # ADR-0001 …
│  └─ operations.md
├─ infrastructure/
│  └─ docker/                  # api.Dockerfile, web.Dockerfile, nginx.conf, web-nginx.conf
├─ docker-compose.yml
├─ .dockerignore
├─ .env.example
├─ .editorconfig
├─ .gitignore
├─ global.json
├─ Directory.Build.props
└─ README.md
```

**Rejected — polyrepo:** the API contract is generated by the backend and consumed by the frontend; splitting them would require cross-repo versioning of `openapi.json` for a single-team MVP. **Rejected — microservices:** explicitly out of scope; a modular monolith with clean module boundaries is sufficient and keeps the deployment to one API container.

## 3. File ownership matrix (strict — no concurrent edits)

| Path | Owner | May read |
|---|---|---|
| `backend/src/Domain/**`, `backend/src/Application/**`, `backend/src/Infrastructure/**`, `backend/src/Api/**`, `backend/tests/**` | **Agent 2** | all |
| `frontend/src/**`, `frontend/e2e/**`, `frontend/*.json`, `frontend/*.ts` | **Agent 3** | all |
| `contracts/openapi.json` | **Agent 2** (generated) — approved by **Agent 1** | all |
| `docs/architecture/**`, `docs/decisions/**` | **Agent 1** | all |
| `infrastructure/docker/**`, `docker-compose.yml`, `.github/workflows/**`, `.gitignore`, `.dockerignore`, `.editorconfig`, `.env.example`, `global.json`, `Directory.Build.props`, `README.md` (setup/deploy sections) | **Agent 5** | all |
| `docs/operations.md` | **Agent 5** | all |
| Security review notes, QA reports | **Agent 4** | all |

**Rules:**
- An agent never edits a path it does not own. A needed change outside ownership is requested from the owner.
- `backend/src/**` and `frontend/src/**` are never touched by Agent 5 without an explicit Architect instruction.
- Only Agent 5 writes to the repository (Mode B). Everyone else publishes files.
- Agent 1 approves the API contract before the frontend consumes it.

## 4. Consequences

**Positive**
- No merge conflicts between agents; a single linear history per phase.
- Every phase has one accountable integrator and one review gate.
- The monorepo keeps the generated contract and its consumer in one place.

**Negative / accepted costs**
- **Serialized delivery** — phases cannot overlap; total wall-clock time is the sum of phases.
- **Handoff overhead** — every file needs a URL and an exact path; a mis-typed path is a failed commit.
- **Single point of failure** — if Agent 5's MCP write path is down (403), the whole pipeline stalls. Mitigation: the artifact bundle fallback (below).
- **No local Docker verification** — image correctness is proven only in CI (`compose-config`) and on a real host at P6.

## 5. Operational rules derived from this ADR

1. **Never** use `encoding: "base64"` with `GITHUB_CREATE_A_BLOB` in Composio MCP — **UTF-8 only**; prefer `GITHUB_CREATE_OR_UPDATE_FILE_CONTENTS` with plain-text `content`.
2. If Composio returns **403 twice**, **stop retrying** and hand off an artifact bundle (published `/sites/...` file + target path + suggested commit message) for the integrator to land later.
3. Re-read a file after any MCP write to confirm content and size actually changed.
4. Branch naming: `feat/p{N}-{scope}` (e.g. `feat/p1-backend-core`). Merge only with green CI, squash.
5. `main` must have branch protection enabled so the "merge only when CI is green" policy is enforced, not decorative.

## 6. Status of this ADR

Accepted. It is the basis for the Phase 0 Contract v1.2 and for the P0→P6 delivery order. Any change to the integration mode, the topology, or the ownership matrix requires a new ADR that supersedes this one.
